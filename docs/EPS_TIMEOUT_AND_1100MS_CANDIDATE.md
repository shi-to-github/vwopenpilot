# 1.1 秒候选与本车 EPS 超时证据

本轮用户要求先把停止时间做到 1.1 秒，并查日志确定本车 EPS 何时开始拒绝控制。只修改本地候选与分析工具，未连接 C2，未部署或改变当前设置。

## 本地改动

新包 candidate/device-a6eed9e-v3-hca-r2-1100ms，基线是实际部署的 hca-r2-entry。保留旧包及原哈希，三文件回退副本保存于新包 rollback/。默认 standby 从两秒改为 1.1 秒，即 50 Hz 下 55 个连续 disabled 命令周期。

控制器传给 Runtime 的启动前暂停时长从写死的两秒改为实际 timer.required/timer.hz；暂停期间仍用剩余时长。Runtime 启动中心漂移预测同步使用 1.1 秒。未来转向评估时域从 2.5 秒改为 1.3 秒（1.1 秒暂停 + 0.2 秒模型新鲜度余量），模型边界插值以覆盖最后一个不整齐的采样间隔。该余量是候选设计参数，不是 EPS 实测值。

本地 8 项测试通过，包含连续 55 帧、54 帧不误记复位、下一周期恢复、原请求中止保留、实际控制器传递 1.1 秒和剩余时长、较晚弯道排除、窗口边界弯道捕获、哈希与回退文件一致。没有更改 150 秒搜索、240 秒新增软件接管、90 请求中止、PID、纵向、Panda 或 EPS。这次尚未实现完整分阶段择机和新的中止策略。

## 跨历史日志审计

扫描本地原始 V3/r1/diag1/r2 与早期探针日志，按文件名去重。共检查 170,819 条原生 EPS 帧；只有一组 EPS rejected（41 帧，约两秒）。早期定速探针日志没有记录 978/EPS 帧，不能拿其长行程证明硬件超时。

共发现 20 次软件 deadline 边沿，来自新增的四分钟门限。这些计时不是硬件内部计时，不能以其退出推断 EPS 是四分钟超时。最新 r2 段的六次退出前仍为 active，未出现 rejected/fault。

此前 boot 1347.786264–1348.666473 有 45 帧、约 0.900 秒 standby。旧 V3 在短暂 lat_active=false 时立即清零软件 elapsed，随后到 EPS 拒绝只显示约 177 秒。这解释了为何界面计时不能直接代表硬件计时，并支持短于一秒的退出没有充分复位硬件累计计时的推断。

综合时间与报文，**本车硬件超时明显更接近累计激活约 360 秒（六分钟），不是当前软件的 240 秒，也没有依据认定为固定五分钟。**这是一次历史事件的强线索；初始约 1.25 秒未保存、EPS 内部计数不可读，不能宣称已精确证明其阈值或完整内部实现。

本次可确认 2.060 秒 standby 后恢复、0.900 秒短退出未避免后续拒绝；尚不能由这两点直接证明 1.1 秒对本车足够，更不能把内部最短值写成已实测的一秒。
